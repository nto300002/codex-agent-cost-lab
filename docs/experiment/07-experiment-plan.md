# Codexコスト比較 実験計画

- ステータス: Draft
- 対象: Codex CLI
- 対象アプリ: TraceCRM
- 主実験条件: P0、P1、P2
- 計画試行数: パイロット45 + 本実験90 = 135
- 実験責任者: 未割当
- 実施期間: 未確定

## 1. 目的

同一のソフトウェア開発タスクに対して、プロンプト構造と最小限の `AGENTS.md` が、次の結果へ与える影響を比較する。

- 成功率
- 成功1件当たり消費クレジット
- 入力、キャッシュ入力、出力、推論出力トークン
- 明示的なファイル参照とリポジトリ横断検索
- テスト実行回数
- 実行時間
- 不要変更、禁止変更
- 人間による追加修正時間

主要な判断対象は、単純なトークン削減ではなく「成功したタスク1件当たりの総コスト」である。

## 2. リサーチクエスチョン

1. P1はP0より、成功率を維持しながらトークンとクレジットを削減できるか。
2. P2はP1より、探索、テスト、再試行を削減できるか。
3. P1/P2の効果はG-A、G-B、G-Cで異なるか。
4. トークン削減は、成功1件当たりクレジットの削減につながるか。
5. 指示の構造化により、不要な参照・変更・テスト実行が減るか。

## 3. 実験条件

| 条件 | タスクプロンプト | リポジトリ指示 |
|---|---|---|
| P0 | 現場で自然に使われる短い依頼 | なし |
| P1 | 目的、範囲、制約、テスト、停止・完了条件を構造化 | なし |
| P2 | P1と同じ構造化プロンプト | 最小限の `AGENTS.md` |

P3の過剰な `AGENTS.md` は主実験へ含めない。予算と時間に余裕がある場合のみ、主実験完了後の別実験として扱う。

### 3.1 比較の公平性

- P0を意図的に極端な悪文にしない。
- P1/P2だけに正解ファイル、原因、隠しテストを開示しない。
- P1とP2のタスク固有プロンプトは同一にする。
- P0/P1実行時は、プロジェクトおよびグローバルの `AGENTS.md` を混入させない。
- プロンプトと `AGENTS.md` の内容・ハッシュを各実行に記録する。

## 4. タスク

| ID | 粒度 | 種別 | 内容 |
|---|---|---|---|
| GA-F1 | G-A | 修正 | 電話番号空文字の500エラー |
| GA-I1 | G-A | 実装 | 顧客一覧への最終更新日時表示 |
| GB-F1 | G-B | 修正 | 担当外Deal更新の認可不具合 |
| GB-I1 | G-B | 実装 | Customer一覧のステータス・担当者絞り込み |
| GC-F1 | G-C | 修正 | Customer削除時の関連データ整合性 |
| GC-I1 | G-C | 実装 | 主要操作への監査ログ追加 |

各タスクは、事前に作成した正解パッチを用いて次を記録する。

- 正解実装の関連ファイル数
- 関係層数
- 受入条件数
- 変更行数
- 必要なテスト
- 熟練エンジニアの標準作業時間

正解パッチ、期待関連ファイル、隠しテストはCodexの作業環境から隔離する。

## 5. 実験マトリクス

### 5.1 パイロット

各粒度から1タスクを選び、P0/P1/P2を各5回実行する。

| タスク | 選定理由 | 条件 | 反復 | 試行数 |
|---|---|---:|---:|---:|
| GA-F1 | 局所修正と空値境界の確認 | 3 | 5 | 15 |
| GB-I1 | UI・API・永続化をまたぐ実装 | 3 | 5 | 15 |
| GC-F1 | 複数機能のトランザクション整合性 | 3 | 5 | 15 |
| 合計 |  |  |  | 45 |

パイロットの目的は効果の結論を出すことではなく、計測欠損、難易度、タイムアウト、予算、評価器を確認することである。

### 5.2 本実験

6タスクすべてについて、P0/P1/P2を各5回実行する。

| 粒度 | タスク数 | 条件数 | 反復 | 試行数 |
|---|---:|---:|---:|---:|
| G-A | 2 | 3 | 5 | 30 |
| G-B | 2 | 3 | 5 | 30 |
| G-C | 2 | 3 | 5 | 30 |
| 合計 | 6 | 3 | 5 | 90 |

パイロットと本実験を合わせた計画試行数は135である。条件変更の有無にかかわらず、パイロット結果は本実験の主要な効果集計へ混ぜず、参考結果として分けて表示する。

## 8. 実行順序

条件を時間帯やサービス状態へ偏らせないため、Seed付きの層化ランダム化を使用する。

1. 反復番号ごとに1ブロックを作る。
2. 各ブロックへ対象となる全タスク×全条件を1回ずつ入れる。
3. ブロック内の順序を固定Seedでシャッフルする。
4. 同じ条件が長く連続する場合も、生成後に手作業で並べ替えない。
5. 生成済みの実行順とSeedを成果物として保存する。

本実験では1ブロック18試行、全5ブロックとする。

## 9. 1試行の実行手順

### 9.1 Preflight

1. run IDが未使用であることを確認する。
2. 開始コミット、タスク、プロンプト、設定のハッシュを検証する。
3. 隔離された新規ワークスペースを作成する。
4. DB、Seed、依存キャッシュを所定状態へ戻す。
5. P2のみ `AGENTS.md` を配置し、P0/P1では存在しないことを確認する。
6. Codexから正解パッチと隠し評価へ到達できないことを確認する。

### 9.2 Execution

1. 新規Codexセッションを開始する。
2. `codex exec --json` を固定設定で実行する。
3. stdoutをJSONL、stderrを別ファイルへ保存する。
4. 開始・終了時刻、終了コード、タイムアウトを記録する。
5. タイムアウト後も部分ログと作業ツリーを保持する。

### 9.3 Evaluation

1. Git差分と未追跡ファイル一覧を保存する。
2. 隠し機能テストを作業環境の外から実行する。
3. 回帰テスト、型チェック、Lintを実行する。
4. 禁止変更と新規依存を検査する。
5. JSONLからトークン、コマンド、参照、検索、テスト回数を抽出する。
6. 成功、品質点、失敗理由を評価JSONへ保存する。
7. 条件を伏せた状態で人間レビューを行う。

### 9.4 Finalize

1. run JSONの必須項目と成果物ハッシュを検査する。
2. rawデータは追記専用として保存する。
3. ワークスペースを次の試行へ再利用しない。
4. 実行台帳へ完了、無効、失敗のいずれかを記録する。

### 9.5 反復間の初期化

反復は、同じ変更状態から作業を続ける再試行ではない。同一の「タスク×条件」を、毎回同じ開始状態から独立して実行する試行である。

```text
GA-F1 × P0 × run01
GA-F1 × P0 × run02
GA-F1 × P0 × run03
GA-F1 × P0 × run04
GA-F1 × P0 × run05
```

各反復では、次の状態を前回から引き継がない。

- Codexが変更した追跡・未追跡ファイル
- Git indexと作業ツリーの状態
- SQLite DBとSeedの変更
- テスト結果、ビルド生成物、一時ファイル
- タスク条件として配置した `AGENTS.md`
- Codexの会話、セッション、タスク固有の記憶

#### 推奨方式

現在の開発用checkoutを直接リセットせず、runごとに同じ基準コミットから一時worktreeを作る。

1. run ID専用の空パスを決定する。
2. タスクの開始コミットからdetached worktreeを作成する。
3. DB、Seed、生成物、条件ファイルを初期化する。
4. 新規Codexセッションで1試行だけ実行する。
5. diff、未追跡ファイル、JSONL、評価結果をworktree外へ保存する。
6. 成果物の存在とハッシュを確認する。
7. 一時worktreeを破棄する。
8. 次の反復では、新しい空のworktreeを作成する。

概念上のコマンド例:

```bash
WORK_ROOT="/path/to/experiment-workspaces"
WORK_DIR="$WORK_ROOT/$RUN_ID"
RESULT_DIR="/path/to/results/raw/$RUN_ID"

git worktree add --detach "$WORK_DIR" "$START_COMMIT"

pnpm --dir "$WORK_DIR" db:reset

# 条件ファイルの配置、Codex実行、外部評価

git -C "$WORK_DIR" diff --binary > "$RESULT_DIR/diff.patch"
git -C "$WORK_DIR" status --porcelain=v1 > "$RESULT_DIR/git-status.txt"

# JSONL、評価結果、diffがRESULT_DIRに存在することを確認してから破棄する
git worktree remove --force "$WORK_DIR"
```

`RESULT_DIR` は一時worktreeの外に置く。破棄前に、JSONL、diff、評価結果、テストログ、manifestが保存されていることを必ず検査する。

#### 安全上の注意

- `git reset --hard` や `git clean -fdx` を、開発者が使用しているcheckoutやリポジトリルートへ実行しない。
- これらのコマンドが必要な場合は、実験ランナーが作成した一時worktree内だけを対象にする。
- 削除対象は、run IDから解決した既知のworktreeパスであることを事前検証する。
- 空の環境変数、`~`、`$HOME`、ワークスペースルートを削除・初期化対象にしない。
- worktreeの破棄に失敗した場合は手動で強制削除せず、そのrunを停止してパスとGit登録状態を確認する。

## 11. 測定指標

### 11.1 主要指標

1. 成功率
2. 成功1件当たり消費クレジット
3. 成功1件当たり総コスト

### 11.2 副指標

- 非キャッシュ入力トークン
- キャッシュ入力トークン
- 出力トークン
- 推論出力トークン
- 実行時間
- 明示的ファイル参照総数・ユニーク数
- リポジトリ横断検索回数
- テスト総数・全テスト回数・再実行回数
- 変更ファイル数・追加行・削除行
- 禁止変更率
- 品質点
- 人間の追加修正時間

推論出力トークンは出力トークンの内訳、キャッシュ入力は入力トークンの内訳として扱い、二重加算しない。

## 12. 成功判定

次をすべて満たす実行を成功とする。

- タスク固有の隠しテストが成功する。
- 必須の回帰テストが成功する。
- 型チェックが成功する。
- 禁止領域を変更していない。
- 無断で新規依存を追加していない。
- API、DB schema、認可等のタスク固有制約を守っている。

Codexの最終メッセージは成功判定へ使用しない。G-Cの品質点は補助指標であり、主要な成功・失敗判定を置き換えない。

## 13. 無効試行・失敗・再実行

### 13.1 無効試行

次はエージェント能力ではなく実験基盤の異常として無効にする。

- Codex開始前に開始コミットやDB復元へ失敗した。
- 誤ったプロンプト、モデル、設定、`AGENTS.md` を使用した。
- JSONL保存先や評価器が実験基盤の不具合で失われた。
- サービス障害によりCodexセッション自体を開始できなかった。
- 正解パッチまたは隠しテストがCodexへ露出した。

### 13.2 有効な失敗

次は実験結果へ含める。

- Codexがタイムアウトした。
- 実装やテストが未完了だった。
- 隠しテスト、回帰テスト、型チェックに失敗した。
- 禁止変更や不要な依存追加を行った。
- JSONL上でCodexが途中終了したが、実験基盤は正常だった。

### 13.3 再実行ルール

- 無効試行のみ、同じ条件で置換試行を1回行う。
- 元の無効試行を削除せず、無効理由と置換run IDを記録する。
- 有効な失敗は再実行で置き換えない。
- 同一セルで無効試行が2回続いた場合は実験を停止し、基盤を調査する。

## 14. 停止条件

次のいずれかに該当した場合、新しい試行を開始しない。

- モデル、CLI、料金体系、開始コミット、評価器が意図せず変わった。
- 隠し評価または正解情報の漏えいが判明した。
- 同一原因の基盤エラーが3試行で発生した。
- rawデータの必須項目欠損が5%を超えた。
- 事前承認したクレジットまたは時間予算の80%に到達し、残り試行を完了できる見込みがない。
- セキュリティ上の問題、秘密情報の記録、外部通信を検出した。

停止後は原因、影響範囲、再開条件を記録する。条件を変更して再開する場合は、新しい実験バージョンとして扱う。

## 15. パイロットのGo/No-Go

### 15.1 予算予測

粒度 `g` のパイロット1試行当たり最大クレジットを `max_credit_g` とする。

```text
本実験の保守的な予測クレジット
= 30 × (max_credit_GA + max_credit_GB + max_credit_GC)
```

同様に最大実行時間から本実験の所要時間上限を予測する。

### 15.2 Go条件

- 45試行の成果物がすべて揃っている。
- 無効試行率が5%以下である。
- 必須指標の欠損がない。
- 正解パッチが全評価を通過する。
- 各タスクで未変更状態と正解状態を区別できる。
- 予測クレジットと所要時間が承認済み上限内である。
- タスク粒度とタイムアウトが妥当である。

### 15.3 No-Go条件

- 条件間で異なる事実情報が混入している。
- キャッシュ、トークン、成功判定を正しく集計できない。
- G-A/G-B/G-Cのいずれかで、評価器が成功と失敗を安定して区別できない。
- 隠し評価の隔離を保証できない。
- 予算超過を避ける実行計画を作れない。

No-Goの場合、問題を修正してパイロットを新しいバージョンで再実施する。修正前のパイロットは本実験へ合算しない。

## 16. 分析計画

### 16.1 比較単位

最初に同一タスク内で比較し、その後、同じ粒度内の2タスクをまとめる。

```text
GA-F1: P0 vs P1 vs P2
GA-I1: P0 vs P1 vs P2
G-A:   P0 vs P1 vs P2
```

G-AとG-Cの生トークン数を直接比較して、プロンプト条件の優劣を判断しない。

### 16.2 集計値

各タスク×条件、各粒度×条件について次を表示する。

- 全5試行の生データ
- 中央値
- 最小値、最大値
- 四分位範囲
- 成功数 / 試行数
- 成功1件当たりクレジット

反復5回では検定力が低いため、p値だけで結論を出さない。効果の方向、絶対差、成功率、タスク間の一貫性を中心に解釈する。

### 16.3 削減率

```text
削減率
= (P0の中央値 - Pxの中央値)
  / P0の中央値 × 100
```

入力、出力、クレジット、実行時間は別々に計算する。成功率が低下した条件のトークン削減を、単独で改善とみなさない。

### 16.4 人間レビュー

- レビュー担当者へP0/P1/P2を知らせない。
- 表示順をランダム化する。
- 正確性、変更の小ささ、設計整合、可読性、保守性、セキュリティを同じrubricで評価する。
- 追加修正時間の開始・終了規則を固定する。

## 17. 意思決定ルール

P1またはP2を組織標準の採用候補とするには、次を満たす必要がある。

1. G-BとG-Cの各粒度で、成功率がP0を下回らない。
2. 成功1件当たりクレジットがP0より低い。片方の粒度が同等の場合は、もう片方で明確に低い。
3. 人間の追加修正時間の中央値が増えていない。
4. 禁止変更率が増えていない。
5. G-B/G-Cの4タスク中3タスク以上で効果の方向が一致する。

G-AだけでP0が有利な場合は、構造化プロンプトを一律適用せず、タスク粒度による使い分けを採用候補とする。

いずれの条件も満たさない場合は「差が確認できなかった」または「この環境では悪化した」と報告し、都合のよい副指標だけで採用判断を行わない。

## 18. バイアス対策

| リスク | 対策 |
|---|---|
| タスク難易度差 | 各粒度に修正・実装を1件ずつ含め、タスク別結果を残す |
| 正解情報の混入 | 条件間の事実量をレビューし、正解資産を隔離する |
| 実行順の偏り | Seed付き層化ランダム化 |
| キャッシュ | cached inputを別集計し、実行順を分散する |
| モデル更新 | 実験期間を短くし、バージョン変更時は別実験にする |
| 評価者バイアス | 条件を伏せた人間レビュー |
| 選択的な再実行 | 無効・失敗・置換の規則を事前固定する |
| 選択的な報告 | rawデータ、失敗、外れ値を含めて公開する |
