# 測定と評価

## 12. 測定指標

### 12.1 主要指標

#### 成功率

```text
成功率 = 隠し評価を通過した実行数 / 全実行数
```

#### 成功1件当たり消費クレジット

```text
成功1件当たり消費クレジット
= 全実行の消費クレジット合計 / 成功した実行数
```

成功数が0の場合は算出不能として扱う。

#### 成功1件当たり総コスト

```text
成功1件当たり総コスト
=（Codexコスト + 人間の確認・修正コスト）/ 成功数
```

### 12.2 トークン指標

`turn.completed.usage`から以下を取得する。

- `input_tokens`
- `cached_input_tokens`
- `output_tokens`
- `reasoning_output_tokens`

#### 非キャッシュ入力

```text
非キャッシュ入力 = input_tokens - cached_input_tokens
```

#### 注意

`reasoning_output_tokens`を料金計算時に `output_tokens`へ二重加算しない。適用中の公式レート表の定義に従う。

### 12.3 料金・クレジット

適用中のCodexレート表を基準に計算する。

```text
消費クレジット =
非キャッシュ入力 / 1,000,000 × 入力レート
+ キャッシュ入力 / 1,000,000 × キャッシュ入力レート
+ 出力 / 1,000,000 × 出力レート
```

モデル名、レート表の確認日、Fast modeの有無を記録する。

円換算を行う場合、実験全体で固定為替を使用し、実支払額ではなく換算値であることを明記する。

### 12.4 ファイル探索指標

Codex CLIのJSONLから、コマンド実行およびファイル変更イベントを抽出する。

記録するもの:

- 明示的ファイル参照総回数
- ユニーク参照ファイル数
- 同一ファイル再参照回数
- リポジトリ横断検索回数
- 指定範囲外ファイル参照数
- 変更ファイル数

#### 閲覧ファイル数の表現

Codexが内部的に読んだ全ファイルを完全に復元できるとは限らない。

発表では「閲覧ファイル数」ではなく、次の表現を推奨する。

> 実行ログ上で明示的に参照されたユニークファイル数

#### 横断検索対象例

- `rg`
- `grep -R`
- `find`
- `git grep`
- ディレクトリ全体を対象にした検索

### 12.5 テスト指標

- テストコマンド総実行回数
- 対象テスト実行回数
- 全テスト実行回数
- 同一テスト再実行回数
- テスト成功回数
- テスト失敗回数

JSONL内のコマンドを解析する。

表記揺れを避けるため、可能であればテスト実行をラッパースクリプトで記録する。ただし、その仕組みは全条件で共通にする。

### 12.6 品質指標

- 隠し機能テスト
- 回帰テスト
- 型チェック
- Lint
- 禁止変更検査
- 新規依存追加検査
- 不要ファイル変更
- セキュリティ上の重大問題
- 人間レビュー評価

## 13. 成功判定

Codexの最終メッセージを成功判定に使用しない。

成功は外部評価によって判定する。

### 13.1 必須条件

- 対象機能の隠しテストが通る
- 回帰テストが通る
- 型チェックが通る
- 禁止された領域を変更していない
- 新規依存を無断で追加していない

### 13.2 タスクごとの追加条件

- 公開API形式を変更していない
- DBスキーマを変更していない
- 権限を弱めていない
- 入力検証を削除していない
- テスト自体を無効化していない

### 13.3 部分点

G-Cでは、完全成功だけでは差が見えにくい可能性があるため、副指標として部分点を使用できる。

例:

| 評価項目 | 点数 |
|---|---:|
| 主要機能 | 40 |
| 境界値 | 15 |
| 回帰テスト | 15 |
| 型・Lint | 10 |
| 制約順守 | 10 |
| 不要変更の少なさ | 10 |

主要指標は成功・失敗の二値とし、部分点は補助指標として扱う。

## 14. 人間による評価

人間のレビュー担当者には、P0・P1・P2のどの条件かを知らせない。

評価項目:

- 正確性
- 変更の小ささ
- 既存設計との整合性
- 可読性
- 保守性
- セキュリティ
- 追加修正に必要な時間

人間の修正時間を計測する場合、担当者と時間計測方法を固定する。

## 15. 集計方法

### 15.1 平均だけを使用しない

エージェント実行は外れ値が大きいため、以下を併記する。

- 中央値
- 最小値
- 最大値
- 四分位範囲
- 成功率

### 15.2 粒度別に比較する

最初に各粒度内で比較する。

```text
G-A: P0 vs P1 vs P2
G-B: P0 vs P1 vs P2
G-C: P0 vs P1 vs P2
```

その後に全体傾向を示す。

G-AとG-Cの生トークン数を単純比較しても、プロンプト効果は分からない。

### 15.3 タスク単位の差を残す

全タスクをまとめた平均だけでなく、タスクごとの結果を表示する。

例:

| Task | Condition | Success | Credits | Unique files | Tests |
|---|---|---:|---:|---:|---:|
| GA-F1 | P0 | 4/5 |  |  |  |
| GA-F1 | P1 | 5/5 |  |  |  |
| GA-F1 | P2 | 5/5 |  |  |  |

### 15.4 削減率

```text
削減率 =
(P0の中央値 - 比較条件の中央値)
÷ P0の中央値 × 100
```

成功率が低下した場合は、トークン削減率を単独で成果として扱わない。

## 16. 実験結果の判断基準

次を満たす場合、組織標準として採用候補とする。

- 成功率がP0より低下していない
- 成功1件当たりクレジットが低下している
- 人間の追加修正時間が増えていない
- 禁止変更率が増えていない
- G-BまたはG-Cで再現性のある効果がある

### 16.1 採用しない例

- トークンは減ったが成功率が低下した
- 入力は減ったが再試行が増えた
- クレジットは減ったが人間の修正時間が増えた
- P2がG-Aでのみ有効で、G-B・G-Cでは悪化した
- 一つのタスクだけで大きな差が出た

## 17. 想定される結果パターン

### パターン1

P1・P2で参照ファイルとテスト回数が減り、成功率が維持される。

評価:

- 有効なコスト削減
- 組織標準化の候補

### パターン2

P2で入力トークンは増えるが、探索と再試行が減り、総クレジットが下がる。

評価:

- `AGENTS.md`の追加入力コストを上回る効果
- 総トークン内訳の説明が必要

### パターン3

G-AではP0が最安、G-B・G-CではP1またはP2が最安になる。

評価:

- タスク粒度に応じた使い分けが必要
- 全タスクへの一律テンプレート適用は不適切

### パターン4

P2またはP3で探索・テストが増え、費用も増える。

評価:

- `AGENTS.md`が過剰
- 指示の削減または階層化が必要

### パターン5

トークン数は減るが成功1件当たりコストは増える。

評価:

- 再試行または失敗率が原因
- トークン削減だけをKPIにしてはいけない
