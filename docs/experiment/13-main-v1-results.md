# Main v1 実測結果とLT向け結論

## 1. 結論

90試行の結果は、指示を詳しくすれば一律に安くなる、という仮説を支持しなかった。効果はタスク粒度とタスク境界に依存した。

- G-AではP2の成功率がP0より20ポイント高く、成功1件当たりcreditsは約34%低かった。
- G-Bでは全条件が100%成功したが、成功1件当たりcreditsはP0が最小だった。
- G-CではP0とP2が90%成功した一方、P1は50%だった。P1の成功1件当たりcreditsはP0の約2.33倍だった。
- 中央値だけを見るとG-BのP1はP0より低いが、成功1件当たりcreditsではP0より高い。1つの代表値だけでは判断できない。

したがって、本実験から提案できるのは「常にP1/P2を使う」ことではなく、粒度ごとに成功率、分布、成功1件当たりコストを計測して使い分けることである。

### G-A

P2はP0に対し、成功率が50%から70%へ上がり、成功1件当たりcreditsが25.97から17.16へ約34%低下した。ただし入力token中央値はP0より大きい。改善は単純なtoken削減ではなく、成功数の増加によって生じている。

タスク別ではGA-F1が全条件5/5成功だった一方、GA-I1はP0 0/5、P1 1/5、P2 2/5だった。粒度集計だけでなくタスク単位の確認が必要である。

### G-B

全条件10/10成功した。credits中央値はP1が最小だが、成功1件当たりcreditsはP0 18.86、P1 19.60、P2 20.14でP0が最小だった。中央値が低いことだけを根拠にP1を採用すると、分布の上側を見落とす。

### G-C

P0とP2は9/10成功し、成功1件当たりcreditsも33.28と33.81で近かった。P1は5/10成功、77.55 credits/成功となった。構造化プロンプトがタスク境界を十分に狭めず、変更・テスト範囲を広げたケースが結果を悪化させた。

## 8. 限界

- 1つのMini CRM、6タスク、1モデル、各条件5反復の結果である。
- G-Aの差はGA-I1、G-Cの差はGC-I1へ集中している。粒度だけを原因と断定できない。
- 人間の修正時間は本実験で実測していないため、総原価の結論には使えない。
- 明示ファイル数はJSONLで確認できた参照であり、モデルが内部で読んだ全ファイル数ではない。
- creditsは固定レートによる再計算値であり、請求額そのものではない。
- 円換算設定の150円/USDは固定シナリオ値であり、実決済為替ではない。
- 成功判定には変更ファイル上限など、この実験固有の制約が含まれる。
- 実行の乱数、キャッシュ状態、モデル提供側の変更を完全には一般化できない。
- G-A/G-B/G-Cの絶対値を粒度間の優劣として比較してはならない。

## 9. LTで使う主張

> 詳しい指示は、それ自体がコスト削減策ではない。小さいタスクでは成功率を上げる場合がある一方、横断タスクでは変更範囲とテストを広げ、成功1件当たりコストを悪化させる場合がある。

> 管理すべき指標は1回のtoken数ではなく、粒度別の分布、成功率、成功した仕事1件当たりのコストである。

再生成手順と各フィールドの定義は[Main v1 再現手順とデータ辞書](14-main-v1-reproduction.md)を参照する。
