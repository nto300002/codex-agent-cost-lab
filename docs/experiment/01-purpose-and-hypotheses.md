# 実験の目的と仮説

## 1. 実験の目的

同一のソフトウェア開発タスクに対して、プロンプトおよび `AGENTS.md` の設計が、Codexの以下の結果へ与える影響を測定する。

- 入力トークン
- キャッシュ済み入力トークン
- 出力トークン
- 消費クレジットまたは料金相当額
- ファイル参照数
- リポジトリ横断検索回数
- テスト実行回数
- 実行時間
- タスク成功率
- 不要変更・禁止変更
- 人間による追加修正量

本実験の最終目的は、単純なトークン削減ではなく、次の指標を改善できるか確認することである。

> 成功したタスク1件当たりの総コスト

---

## 2. 実験上の重要な設計判断

### 2.1 二つの比較軸を分離する

タスク粒度とプロンプト条件を、同じA・B・Cで表現しない。

本実験では以下の名称を使用する。

#### タスク粒度

- `G-A`: 局所タスク
- `G-B`: 複数層タスク
- `G-C`: 横断タスク

#### プロンプト条件

- `P0`: 通常の短い依頼
- `P1`: 構造化プロンプト
- `P2`: 最小限の `AGENTS.md` + 構造化プロンプト
- `P3`: 過剰な `AGENTS.md` + 構造化プロンプト（任意の負の対照条件）

タスク粒度とプロンプト条件を分離しない場合、結果の差がタスク規模によるものか、プロンプト設計によるものか判断できなくなる。

### 2.2 小さいタスクだけで結論を出さない

小規模なタスクでは、Codexが最初の探索で正しいファイルへ到達しやすく、プロンプト条件の差が表れない可能性がある。

一方、大規模なタスクだけでは以下の問題がある。

- 失敗率が高くなりすぎる
- タスクごとの難易度差が大きくなる
- 実行時間とクレジット消費が膨らむ
- 原因分析が困難になる

したがって、`G-A`、`G-B`、`G-C`の3段階で実験する。

## 3. リサーチクエスチョン

### RQ1

構造化プロンプトは、通常の短い依頼と比較して、成功率を維持しながらトークン消費とクレジット消費を削減できるか。

### RQ2

最小限の `AGENTS.md` は、構造化プロンプトだけの場合より、探索・テスト・再試行を削減できるか。

### RQ3

プロンプトおよび `AGENTS.md` の効果は、タスク粒度によって変化するか。

### RQ4

トークン数の削減は、実際の消費クレジットおよび成功1件当たりコストの削減につながるか。

### RQ5

プロンプトを詳細化することで、Codexが参照するファイル数、検索回数、テスト回数、不要変更数は変化するか。

---

## 4. 仮説

### H1

`P1`および`P2`は、`P0`よりも対象外ファイルの参照とリポジトリ横断検索を減らす。

### H2

`P2`の効果は、局所的な`G-A`よりも、探索範囲が広い`G-B`および`G-C`で表れやすい。

### H3

`G-A`では、構造化プロンプトや `AGENTS.md` 自体の入力コストが、削減効果を上回る場合がある。

### H4

過剰な指示を含む`P3`は、Codexが指示へ従って探索・テストを増やすため、`P2`より高コストになる可能性がある。

### H5

総トークン数だけでなく成功率を考慮すると、条件間の優劣が逆転する場合がある。

## 5. 対象環境

### 5.1 エージェント

- Codex CLI
- 非対話モード `codex exec`
- JSONL出力 `--json`
- 実験時点で利用可能な同一モデルに固定
- 同一の reasoning effort に固定
- 同一のsandbox設定に固定

Codex CLIのバージョン、モデル名、実行日時を毎回記録する。

### 5.2 対象リポジトリ

次の条件を満たす実験用リポジトリを使用する。

- Git管理されている
- 自動テストが存在する
- 型チェックまたは静的解析が存在する
- 複数の機能領域を持つ
- UI、API、ドメインロジック、永続化層のうち複数を含む
- 生成物、依存パッケージ、秘密情報を含まない
- 各タスクの開始コミットを固定できる
- 隠し評価テストをCodexから隔離できる

小さすぎるサンプルリポジトリは避ける。目安として、複数のディレクトリと機能領域を持ち、Codexが探索経路を選択する余地があることを重視する。

### 5.3 ネットワーク

原則としてネットワークアクセスを無効にする。

外部ドキュメント検索が必要なタスクを混ぜる場合は、全条件で同一のネットワーク設定にする。
