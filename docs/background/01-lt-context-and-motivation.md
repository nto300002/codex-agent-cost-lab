# LTの文脈と実験の動機

## 1. 元となるLTスライド

本実験は、次のLTを支えるために実施する。

### 発表タイトル

**AIエージェントのトークン消費とコスト管理という経営課題に立ち向かう**

### 副題

**そのプロンプト、何円分の寄り道をさせていますか？**

### 発表の中心的な問い

AIコーディングエージェントへ曖昧な依頼を与えた場合と、調査範囲・変更制約・完了条件・停止条件を明確にした場合では、次の結果にどの程度の差が生じるのか。

* トークン消費量
* 消費クレジット・料金相当額
* ファイル探索量
* テスト実行回数
* 実行時間
* タスク成功率
* 不要な変更
* 人間による追加修正量

発表では、単に「良いプロンプトの書き方」を紹介するのではなく、個人の依頼方法の違いが、組織全体ではどの程度の開発原価差になるかを示す。

---

## 2. この実験が必要な背景

AIエージェントは、通常のチャットAIとは異なり、一度回答して終了するわけではない。

Codexはタスクを受け取ると、必要に応じて次の処理を繰り返す。

1. 指示とリポジトリ構成を確認する
2. コードを検索する
3. 関連ファイルを読む
4. 原因や実装方法を推測する
5. コードを変更する
6. テストや型チェックを実行する
7. 失敗結果を読み込む
8. 再調査・再修正する

この一連の実行軌跡がコンテキストへ蓄積され、後続ターンでも入力される。そのため、利用者が入力したプロンプトが短くても、探索範囲や再試行回数が大きければ、総トークン消費は増える。

2026年の研究では、同じコーディングタスクを同一条件で実行しても、総トークン消費に最大30倍の差が生じたと報告されている。また、トークンを多く使った実行ほど成功率が高いとは限らず、入力トークンがエージェント型タスクの主なコスト要因になるとされている。

したがって、AIエージェントの費用は、モデルの単価だけでは予測できない。

> 何を調べさせ、どこまで変更させ、何回まで試行させるか

という仕事の与え方そのものが、コストを左右する。

## 3. 実験で検証する内容

本実験では、同一の開発タスクを次の3条件でCodexへ実行させる。

### P0：通常の短い依頼

現場で自然に使用される程度の短いプロンプトを与える。

例：

> 顧客編集画面で電話番号を空欄にすると500エラーになります。原因を調べて修正し、必要なテストを実行してください。

意図的に極端に悪いプロンプトにはしない。

### P1：構造化プロンプト

次の情報を明示する。

* 目的
* 再現条件
* 最初に調べる範囲
* 変更してよい範囲
* 変更禁止範囲
* テスト方針
* 停止条件
* 完了条件
* 最終報告形式

### P2：最小限のAGENTS.md＋構造化プロンプト

P1に加え、リポジトリ全体で繰り返し必要になる情報を`AGENTS.md`へ記載する。

* 技術構成
* ディレクトリの責務
* 正式なテストコマンド
* 最小変更の原則
* 新規依存追加の制限
* 変更禁止領域
* 停止条件

Codexは作業開始前に`AGENTS.md`を読み、グローバルな指示とプロジェクト固有の指示を階層的に組み合わせる。

ある研究では、`AGENTS.md`を使用した条件で実行時間中央値が28.64%、出力トークンが16.58%減少し、タスク完了挙動は同程度だったと報告されている。ただし、すべてのリポジトリやタスクで同じ削減率になることを示すものではない。

## 4. 元となる実験用アプリ

実験対象には、受託開発で一般的な顧客・商談管理システムを模した、実験専用Mini CRM「TraceCRM」を使用する。

主な機能は次のとおりである。

* ログイン
* ユーザー・ロール管理
* 顧客管理
* 商談管理
* 活動履歴
* 顧客検索・絞り込み
* CSV出力
* 操作監査ログ

技術構成は、Next.js、TypeScript、Prisma、SQLite、Zod、Vitest、Playwrightを想定する。

Todoアプリのような小規模アプリでは、Codexが正しいファイルを容易に発見できるため、プロンプト条件による探索差が現れにくい。一方、巨大なOSSでは外部依存やビルド時間などのノイズが大きくなる。

TraceCRMは、その中間として次の条件を満たすように設計する。

* 複数の機能領域がある
* UI、API、ドメイン、永続化層が分かれている
* 自動テストがある
* Codexが探索経路を選択する余地がある
* 外部サービスなしで動作する
* 毎回同じGitコミットとDB状態へ戻せる
* 隠しテストと正解パッチをCodexから隔離できる

## 5. タスク粒度を分ける理由

小規模な修正だけを比較すると、P0でもすぐに正解へ到達し、プロンプト設計の差がほとんど出ない可能性がある。

そこで、開発タスクを3段階に分ける。

### G-A：局所タスク

* 関連ファイル：1〜3件
* 関係する層：1層
* 人間の作業目安：15〜30分

例：

* 電話番号の空文字で500エラーになる問題の修正
* 顧客一覧への更新日時表示

### G-B：複数層タスク

* 関連ファイル：4〜8件
* 関係する層：2〜3層
* 人間の作業目安：1〜2時間

例：

* 担当外商談を更新できる認可不具合
* 顧客一覧へのステータス・担当者絞り込み

### G-C：横断タスク

* 関連ファイル：9〜20件
* 関係する層：3層以上
* 人間の作業目安：半日程度

例：

* 顧客削除時の関連データ不整合
* 顧客・商談・ユーザー操作への監査ログ追加

各粒度に、修正タスクと新規実装タスクを最低1件ずつ用意する。

比較するのはG-AとG-Cの絶対トークン数ではない。各粒度の内部で、P0・P1・P2による差を見る。

## 6. 結果を見せる対象

### 主な対象者

LT会へ参加する受託開発エンジニアを主対象とする。

発表では、管理会計や経営理論を中心に扱うのではなく、次のような技術者が直接確認できる結果を示す。

* Codexが何ファイルを参照したか
* リポジトリ全体を何回検索したか
* テストを何回実行したか
* どれだけトークンを使ったか
* 最終的に修正へ成功したか
* 無関係なファイルを変更したか
* 実行1回当たり何クレジット消費したか

その上で、結果を100人規模のシステム会社へ換算し、個人の小さな差が組織全体ではどの程度の金額になるかを示す。

### 結果の比較対象

各実行について、次の値を記録する。

| 分類   | 指標                      |
| ---- | ----------------------- |
| トークン | 入力、キャッシュ入力、出力、推論出力      |
| コスト  | 消費クレジット、料金相当額           |
| 探索   | 明示的ファイル参照、ユニークファイル、横断検索 |
| 実行   | コマンド数、テスト回数、実行時間        |
| 品質   | 隠しテスト、回帰テスト、禁止変更        |
| 成果   | 成功率、成功1件当たりコスト          |
| 人間側  | 追加修正時間、レビュー指摘           |

Codex CLIの`codex exec --json`を使用すると、実行イベントをJSONLとして出力できる。イベントにはコマンド実行、ファイル変更、ターンの開始・完了などが含まれ、`turn.completed`には入力・キャッシュ入力・出力・推論出力のトークン数が含まれる。
